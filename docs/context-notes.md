# Context Notes: 교사 전용 나눔·소모임 플랫폼

`implement`가 같은 탐색을 반복하지 않도록 정리한 기반 노트다.

## 코드베이스 현황

- 탐색 결과 **기존 코드베이스가 없다.** 작업 디렉터리와 업로드 경로 모두 비어 있었다.
  `package.json`, `prisma/`, `drizzle.config.ts`, `supabase/`, `.env.example`,
  `CLAUDE.md`, `README.md` 어느 것도 존재하지 않는다.
- 따라서 이 PRD는 그린필드 전제로 쓰였다. 따라야 할 기존 관례가 없으므로 스택 기본값과
  사용자 지정 사항이 유일한 제약이다.

## 스택 근거

- React + Next.js (App Router), TypeScript — 기본 스택. 사용자도 "react, next's"로 지정.
- Supabase (Postgres) — **사용자가 직접 지정**했다. 저장소 탐색으로 확인할 근거는 없었고,
  지정이 명확하므로 데이터베이스 확정 질문은 하지 않았다.
- ORM 없음. `@supabase/supabase-js` + `@supabase/ssr`로 직접 접근하고, 스키마는
  `supabase/migrations/`의 SQL로 관리한다. Auth·Storage·RLS를 함께 쓰는 구성에서
  ORM을 얹으면 정책과 마이그레이션이 두 곳으로 갈라지기 때문이다.

## 카카오 학교 검색 조사 결과

- 사용할 API: **카카오 로컬(Local) REST API — 키워드로 장소 검색**
  - `GET https://dapi.kakao.com/v2/local/search/keyword.json`
  - 헤더: `Authorization: KakaoAK <REST_API_KEY>`
  - 파라미터: `query`(검색어), `category_group_code=SC4`(학교)
- 응답 `documents[]`에서 쓰는 필드: `id`(장소 ID, 고유 키로 사용), `place_name`,
  `road_address_name`, `address_name`, `x`(경도), `y`(위도).
- 지도를 그리지 않으므로 Kakao Maps JavaScript SDK는 필요 없다. REST 호출만 한다.
- REST 키는 서버 전용이다. 라우트 핸들러에서 프록시하고 `NEXT_PUBLIC_` 접두사를 쓰지 않는다.
- `SC4`는 학교 카테고리지만 학원(`AC5`)·유치원(`PS3`)이 별도 코드로 있음에도 결과에
  섞일 수 있다. 정확한 학교 코드·설립구분이 필요해지면 NEIS 학교기본정보 API로
  보강하는 게 맞지만 MVP 범위 밖이다.
- 페이징 한계: `size` 최대 15, `page` 최대 45, `pageable_count` 최대 45. 즉 한 검색어로
  최대 45개까지만 볼 수 있다. 학교 검색에는 충분하다.
- 거리 관련 (조사만 하고 MVP에 넣지 않음):
  - 요청에 `x`, `y`를 주면 응답 document에 `distance`(미터, 중심좌표까지의 직선거리)가
    붙고 `sort=distance`로 정렬된다. `radius`는 최대 20,000m다.
  - 이미 저장된 두 학교 사이 거리는 API 없이 저장된 좌표로 하버사인 계산이 가능하다.
    20km 제한도 쿼터 소모도 없다. 거리 기능을 넣게 되면 이 방식을 쓴다.
  - 도로 기준 이동거리·소요시간은 로컬 API에 없다. 카카오모빌리티 길찾기 API가 필요하고
    별도 제품이다.
- **저장 허용 범위는 미확인.** 카카오 API 응답 데이터를 자체 DB에 저장·캐싱하는 것이
  약관상 어디까지 허용되는지 확인하지 못했다. 데브톡에 반복 문의되는 주제다.
  캐싱 요구사항 때문에 저장 범위가 검색 결과 전체로 넓어졌으므로, T21 착수 전에
  반드시 확인해야 한다. PRD의 `Risks And Open Decisions` 첫 항목이다.

## 결정해 둔 설계 포인트

- **탄소량은 스냅샷.** `item_types.carbon_g`를 글 작성 시점에 `share_posts.carbon_g`로
  복사한다. 계수 표를 나중에 바꿔도 과거 글은 그대로다. 누적치는 `completed` 글만 합산한다.
- **댓글 테이블은 분리.** `share_comments`와 `club_comments`를 따로 둔다. 나눔 댓글에만
  "예약중 차단" 규칙이 붙기 때문에 다형(polymorphic) 단일 테이블로 묶으면 정책이 지저분해진다.
- **규칙은 DB에서 강제.** 사진 장수, 상태 전이, 예약중 댓글 차단, 카테고리 짝은 모두
  트리거와 `CHECK`로 막는다. 화면 검증은 UX용이고 신뢰 경계가 아니다.
- **승인 게이트는 이중.** `middleware.ts`는 리다이렉트만 담당하고, 실제 차단은 RLS의
  `is_approved()`가 한다. 검증도 RLS 쪽을 본다.
- **`profiles` 본인 행 읽기는 예외.** 승인 대기 화면이 자기 상태를 읽어야 하므로
  이 정책만 `status` 조건에서 빠진다. 이 예외가 다른 테이블로 새지 않는지 확인이 필요하다.
- **관리자 승격 화면 없음.** 최초 관리자는 Supabase 대시보드에서 수동으로 만든다.
- **카카오 호출은 한 파일에만.** `app/api/schools/search/route.ts` 밖에서 카카오를
  호출하면 캐시가 새고 호출 횟수 검증(AC18~AC20)이 불가능해진다.
- **캐시 키는 정규화된 문자열 완전 일치.** 앞뒤 공백 제거 + 연속 공백 1칸 + 소문자.
  유사어 매칭이나 부분 일치 재사용은 하지 않는다. 히트율보다 예측 가능성을 택했다.
- **캐시·`schools` 쓰기는 서비스 롤 전용.** 두 테이블에 사용자 세션용 쓰기 정책을
  아예 만들지 않는다. 정책이 없으면 RLS가 켜진 테이블은 거부하므로 별도 방어가 필요 없다.
- **탄소량은 본인만 본다.** 랭킹은 한 번 넣었다가 사용자 요청으로 제거했다. 다른
  사용자의 탄소량을 노출하는 화면은 만들지 않는다. `user_carbon_totals`는 본인 조회용이다.

반드시 둘 다 고쳐야 한다.

## 아직 안 정한 것

세 가지가 잠정 기본값으로 진행 중이다. 상세는 PRD의 `Risks And Open Decisions` 참고.

1. 가입 승인 기준 — 잠정: 관리자 수동 승인만
2. 탄소량 부여 방식 — 잠정: 글쓴이가 품목 유형 선택 → 계수 자동 부여
3. 평가 질문 세트 — 잠정: 전국 공통 1세트

세 결정 모두 스키마를 바꾼다. 구현 도중 사용자가 다른 답을 주면 T5, T7/T10, T16의
마이그레이션을 다시 봐야 한다.

여기에 더해, 카카오 응답 저장 범위 확인은 **결정이 아니라 막는 확인 사항**이다.
답이 부정적이면 캐시 설계 전체를 다시 짜야 한다.
