# PRD: 교사 전용 나눔·소모임 플랫폼

## Summary

승인된 현직 교사만 이용하는 웹 플랫폼을 만든다. 핵심 가치는 두 가지다. (1) 쓰던 교육용
물건을 다른 교사에게 나눔하고, 그 결과를 절약한 탄소량으로 돌려받는다. (2) 교사끼리
소모임을 열고 참여자를 모은다. 여기에 학교 정보 탭을 더해, 교사가 자기 학교나 관심 학교를
검색하고 운영자가 등록한 질문에 별점을 매길 수 있게 한다.

MVP 범위는 4개 탭(나눔 / 소모임 / 학교정보 / 내 설정), 이메일 가입 + 관리자 승인,
카테고리 체계 1종, 별점 평균 집계, 학교 검색 결과 캐싱까지다.

## Problem And Goal

**문제**

- 교사가 쓰던 교구·학급 물품은 학기말에 대부분 폐기된다. 같은 물건을 옆 학교 교사가
  자비로 다시 산다. 교사끼리 물건을 주고받을 신뢰 가능한 창구가 없다.
- 일반 중고 플랫폼은 교사 인증이 없어 학교 맥락(학교급, 과목, 학급자료)을 담지 못하고,
  판매·흥정 중심이라 나눔 문화와 맞지 않는다.
- 소모임 모집도 마찬가지로 학교 밖 커뮤니티에 흩어져 있다.

**목표**

- 승인된 교사만 들어오는 폐쇄형 공간에서, 물건 나눔 글을 올리고 예약·완료까지 끝낸다.
- 나눔 완료 실적을 탄소 절감량으로 환산해 개인 프로필에 누적한다.
- 같은 계정 체계 위에서 소모임 모집 게시판을 함께 운영한다.
- 학교별 평판을 별점으로 축적한다.

**성공 기준 (MVP)**

- 교사가 가입 → 승인 → 나눔 글 작성 → 다른 교사가 예약 → 나눔 완료 → 탄소량 적립까지
  중단 없이 이어진다.
- 승인되지 않은 계정은 어떤 게시글 데이터에도 접근하지 못한다.

## Users And Use Cases

**교사 (일반 사용자)**

- 이메일로 가입하고 학교 이름과 성함을 입력한 뒤 승인을 기다린다.
- 나눔 탭에서 학교급·카테고리로 물건을 걸러 보고, 마음에 들면 댓글을 남긴다.
- 물건을 예약하고, 받은 뒤 글쓴이가 나눔 완료로 바꾼다.
- 소모임 탭에서 모임을 열거나 댓글로 참여 의사를 밝힌다.
- 학교정보 탭에서 학교를 검색해 별점을 매기고, 다른 교사의 평균 점수를 본다.
- 내 설정 탭에서 닉네임·학교를 바꾸고, 내가 쓴 글과 누적 탄소량을 확인한다.

**관리자 (운영자)**

- 가입 신청 목록을 보고 승인 또는 거절한다.
- 학교 평가 질문 세트를 등록·수정한다.
- 품목 유형별 탄소 계수 표를 관리한다.

## Pre-Work

구현 전에 아래를 준비한다. 코드 작업이 아니라 계정·프로젝트 세팅이다.

1. Supabase 프로젝트 생성. Auth의 Email 제공자를 켜고 이메일 확인(confirm email)을 활성화한다.
2. Storage 버킷 두 개 생성: `share-images`, `club-images`. 둘 다 비공개로 두고 서명 URL로 읽는다.
3. 카카오 개발자 콘솔에서 애플리케이션을 만들고 REST API 키를 발급받는다. 플랫폼 등록은
   서버 사이드 호출이므로 도메인 등록 없이도 동작하지만, 운영 도메인은 등록해 둔다.
4. 최초 관리자 계정 1개를 수동으로 만든다. Supabase 대시보드에서 사용자를 생성한 뒤
   `profiles.role`을 `admin`, `status`를 `approved`로 직접 바꾼다. 관리자 승격 화면은 MVP에 없다.
5. 로컬 `.env.local`에 아래 이름의 환경 변수를 채운다. 값은 이 문서에 적지 않는다.
   - `NEXT_PUBLIC_SUPABASE_URL`
   - `NEXT_PUBLIC_SUPABASE_ANON_KEY`
   - `SUPABASE_SERVICE_ROLE_KEY`
   - `KAKAO_REST_API_KEY`

## Non-Goals

아래는 MVP에서 만들지 않는다. 좋아 보여도 이번 범위에 넣지 않는다.

- 실시간 채팅, 1:1 DM, 푸시 알림, 이메일 알림.
- 소모임 멤버십. 소모임은 게시글 + 댓글 게시판이다. 가입 신청, 정원, 참여자 명단,
  일정 관리, 소모임 전용 공간은 만들지 않는다.
- 결제, 배송, 택배 연동, 거래 후기, 신고, 차단, 좋아요, 북마크.
- 학교 이메일 도메인 자동 인증, 재직 증명 파일 업로드 검증.
- 전체 통합 검색. 검색은 학교정보 탭의 학교 검색만 존재한다.
- 지도 렌더링. 카카오 지도를 화면에 그리지 않는다. 학교 검색 결과는 목록으로만 보여준다.
- 탄소량 랭킹, 리더보드, 배지, 등급, 칭호. 탄소량은 본인 프로필에서 본인 것만 본다.
  다른 사용자의 탄소량을 노출하는 화면은 만들지 않는다.
- 캐시 관리 화면, 수동 캐시 무효화, 캐시 통계.
- 부분 캐시 갱신 전략(stale-while-revalidate, 배경 재검증 등). 캐시는 유효기간이
  지났을 때만 다시 채운다.
- 모바일 네이티브 앱. 반응형 웹까지만 한다.
- 게시글 수정 이력, 소프트 삭제 복구.

## Requirements

### 계정과 접근 제어

- **R1** 방문자는 이메일과 비밀번호로 가입할 수 있다. 가입 폼은 이메일, 비밀번호,
  성함, 학교, 닉네임을 받는다. 학교는 학교 검색(R21)으로 선택한다.
- **R2** 가입 직후 계정의 상태는 `pending`이다. `pending` 계정은 로그인은 되지만
  나눔·소모임·학교정보 탭에 접근하면 "승인 대기 중" 안내 화면으로 대체된다.
- **R3** 관리자는 관리자 화면에서 `pending` 계정 목록(이메일, 성함, 학교, 신청일)을 보고
  개별 승인 또는 거절할 수 있다.
- **R4** 승인된 계정만 게시글·댓글·별점 데이터를 읽고 쓸 수 있다. 이 제한은 화면 라우팅과
  데이터베이스 Row Level Security 양쪽에서 강제한다. 클라이언트 라우팅만으로 막지 않는다.
- **R5** 거절된 계정은 로그인 시 거절 안내를 보고, 어떤 데이터에도 접근하지 못한다.

### 공통 카테고리 체계

- **R6** 나눔 게시글과 소모임 게시글은 모두 학교급 하나와 세부 카테고리 하나를 반드시 가진다.
  - 학교급 `elementary`: 수업자료, 학급자료
  - 학교급 `secondary`: 국어, 수학, 사회, 영어, 역사, 과학, 기술, 미술, 음악, 체육
- **R7** 세부 카테고리는 선택된 학교급에 속한 값만 고를 수 있다. 다른 학교급의 값이
  저장되면 데이터베이스가 거부한다.
- **R8** 나눔 탭과 소모임 탭은 학교급과 세부 카테고리로 목록을 필터할 수 있다.
  필터를 걸지 않으면 전체가 보인다.

### 기능1 — 물건 나눔

- **R9** 승인된 교사는 나눔 글을 작성할 수 있다. 필드는 제목, 물건 설명, 학교급,
  세부 카테고리, 품목 유형, 사진이다.
- **R10** 사진은 1장 이상 4장 이하를 첨부한다. 4장을 초과하면 저장되지 않는다.
- **R11** 나눔 글은 `available`(나눔중), `reserved`(예약중), `completed`(나눔완료) 중
  하나의 상태를 가지며, 목록과 상세에 태그로 표시된다. 새 글의 상태는 `available`이다.
- **R12** 글쓴이가 아닌 승인 교사는 `available` 상태의 글을 예약할 수 있다. 예약하면
  상태가 `reserved`로 바뀌고 예약자가 기록된다. 이미 `reserved` 또는 `completed`인 글은
  예약할 수 없다.
- **R13** 예약자 본인 또는 글쓴이는 예약을 취소할 수 있다. 취소하면 상태가 `available`로
  돌아가고 예약자 기록이 지워진다.
- **R14** 글쓴이만 `reserved` 상태의 글을 `completed`로 바꿀 수 있다. `completed`가 된 글은
  다시 다른 상태로 되돌릴 수 없다.
- **R15** 승인 교사는 나눔 글에 댓글을 달 수 있다. 단, 글의 상태가 `reserved`인 동안에는
  새 댓글을 쓸 수 없고 입력창이 비활성화된다. 이미 달린 댓글은 계속 보인다.
  `completed` 상태에서는 댓글을 쓸 수 있다.
- **R16** 나눔 글 작성 시 고른 품목 유형에 매핑된 탄소 계수(g)가 글에 함께 저장된다.
  계수 표는 관리자만 수정할 수 있다.
- **R17** 사용자의 누적 탄소 절감량은 그 사용자가 쓴 글 중 `completed` 상태인 글의
  탄소 계수 합이다. `completed`가 아닌 글은 합산되지 않는다.

### 기능2 — 소모임

- **R18** 승인된 교사는 소모임 글을 작성할 수 있다. 필드는 제목, 소모임 설명, 학교급,
  세부 카테고리, 사진이다.
- **R19** 사진은 0장 이상 2장 이하를 첨부한다. 2장을 초과하면 저장되지 않는다.
- **R20** 승인 교사는 소모임 글에 댓글을 달 수 있다. 소모임 글에는 예약 개념이 없으므로
  댓글이 상태에 따라 막히지 않는다.

### 기능3 — 학교 정보

- **R21** 승인 교사는 학교 이름 일부를 입력해 학교를 검색할 수 있다. 검색은 서버 라우트
  핸들러가 카카오 로컬 API의 키워드 장소 검색을 `category_group_code=SC4`(학교)로 호출해
  수행한다. 카카오 REST 키는 브라우저에 노출되지 않는다.
- **R22** 카카오 검색 결과로 돌아온 학교는 사용자가 선택했는지와 무관하게 전부
  `schools`에 저장한다. 카카오 장소 ID가 고유 키이며, 이미 있으면 새로 만들지 않고
  기존 레코드를 쓴다. 저장 항목은 학교명, 주소, 위도, 경도, 카카오 장소 ID다.
- **R23** 학교 상세 화면은 운영자가 등록한 평가 질문 목록과 각 질문의 평균 별점,
  그리고 전체 평균 별점, 참여자 수를 보여준다.
- **R24** 승인 교사는 학교마다 질문별로 1~5점을 매길 수 있다. 한 사용자는 한 학교에
  하나의 평가만 가진다. 다시 평가하면 기존 평가를 덮어쓴다.
- **R25** 평균 별점은 해당 질문에 매겨진 모든 점수의 산술 평균이며 소수 첫째 자리까지
  표시한다. 평가가 하나도 없으면 점수 대신 "평가 없음"을 표시한다.
- **R26** 관리자는 평가 질문을 추가·수정·비활성화할 수 있다. 비활성화된 질문은 새 평가
  화면에 나오지 않지만 기존 답변과 평균은 유지된다.

### 기능4 — 내 설정

- **R27** 내 설정 탭은 닉네임, 소속 학교(학교 검색으로 변경), 학교 위치(주소)를 보여주고
  닉네임과 학교를 수정할 수 있다.
- **R28** 내 설정 탭은 누적 탄소 절감량(R17)과 내가 쓴 글 모아보기를 제공한다.
  모아보기는 나눔 글과 소모임 글을 구분해 최신순으로 나열한다.
- **R29** 닉네임은 전체에서 고유하다. 이미 쓰이는 닉네임은 저장되지 않는다.
  게시글과 댓글에는 성함이 아니라 닉네임이 표시된다.

### 기능5 — 학교 검색 캐시

- **R30** 학교 검색어는 정규화한 뒤 캐시 키로 쓴다. 정규화는 앞뒤 공백 제거, 연속 공백
  1칸 축약, 소문자 변환이다. 같은 정규화 키의 유효한 캐시가 있으면 카카오 API를
  호출하지 않고, 캐시에 기록된 학교를 `schools`에서 읽어 결과를 만든다.
- **R31** 캐시가 없거나 유효기간이 지난 검색어만 카카오 API를 호출한다. 호출한 뒤에는
  결과 학교를 전부 `schools`에 저장하고(R22), 정규화 키·결과 학교 목록·결과 순서·
  조회 시각을 캐시에 기록한다.
- **R32** 캐시 유효기간은 90일이다. 만료된 캐시 항목은 지우지 않고 재조회 결과로
  덮어쓴다. 유효기간 안에는 새로 생긴 학교가 검색 결과에 나타나지 않는다.
  이건 의도한 트레이드오프다.
- **R33** 캐시된 결과의 노출 순서는 카카오가 돌려준 순서와 같아야 한다.
- **R34** 캐시와 `schools` 쓰기는 서버에서만 일어난다. 사용자 세션 권한으로는 두
  테이블에 쓸 수 없다.

## Acceptance Criteria

- **AC1** (R1, R2) 새 이메일로 가입을 마치면 `profiles` 행이 하나 생기고 `status`가
  `pending`이다. 그 계정으로 `/share`에 접근하면 승인 대기 화면이 나온다.
- **AC2** (R3) 관리자 계정으로 `/admin/approvals`에 들어가면 위 계정이 목록에 있고,
  승인 버튼을 누르면 `status`가 `approved`로 바뀌며 목록에서 사라진다.
- **AC3** (R4) 승인되지 않은 계정의 액세스 토큰으로 `share_posts`를 직접 조회하면
  RLS에 의해 0행이 반환된다. 화면 우회가 아니라 데이터베이스 수준에서 막힌다.
- **AC4** (R6, R7) 학교급을 `elementary`로 두고 세부 카테고리에 `수학`을 넣어 저장하면
  데이터베이스 제약 위반으로 실패한다.

## Technical Structure And Changes

**스택**

- 프레임워크: React + Next.js (App Router), TypeScript. 기본 스택 그대로다.
- 데이터베이스: **Supabase (Postgres)**. 사용자가 명시적으로 지정했다. 저장소가 비어 있는
  신규 프로젝트라 기존 설정에서 유추할 근거는 없다.
- 접근 계층: `@supabase/supabase-js` + `@supabase/ssr`. ORM은 쓰지 않고 Supabase 클라이언트로
  직접 접근한다. 스키마는 `supabase/migrations/`의 SQL 파일로 관리한다.
- 인증: Supabase Auth (이메일 + 비밀번호).
- 파일: Supabase Storage.
- 외부 API: 카카오 로컬 REST API (키워드 장소 검색).

**환경 변수 (이름만)**

- `NEXT_PUBLIC_SUPABASE_URL`
- `NEXT_PUBLIC_SUPABASE_ANON_KEY`
- `SUPABASE_SERVICE_ROLE_KEY` — 서버 전용. 관리자 승인 처리에만 쓴다.
- `KAKAO_REST_API_KEY` — 서버 전용. `NEXT_PUBLIC_` 접두사를 붙이지 않는다.

**데이터 접근 위치**

- 목록·상세 조회는 서버 컴포넌트에서 Supabase 서버 클라이언트로 수행한다.
- 작성·예약·상태 변경·평가 제출 등 쓰기는 Server Actions로 처리한다.
- 카카오 학교 검색만 라우트 핸들러(`app/api/schools/search/route.ts`)를 쓴다.
  클라이언트에서 타이핑에 따라 호출해야 하고 키를 숨겨야 하기 때문이다.

**신규 테이블 (모두 신규, 기존 스키마 변경 없음)**

| 테이블 | 용도 | 주요 컬럼 |
| --- | --- | --- |

| `schools` | 카카오에서 가져온 학교 | `id`, `kakao_place_id`(unique), `name`, `address`, `lat`, `lng` |
| `item_types` | 품목 유형과 탄소 계수 | `id`, `label`, `carbon_g` |
| `share_posts` | 나눔 글 | `id`, `author_id`, `title`, `description`, `school_level`, `category`, `item_type_id`, `carbon_g`, `status`, `reserved_by`, `reserved_at`, `completed_at` |
| `share_post_images` | 나눔 사진 (최대 4) | `id`, `post_id`, `storage_path`, `sort_order` |
| `share_comments` | 나눔 댓글 | `id`, `post_id`, `author_id`, `body` |
| `club_posts` | 소모임 글 | `id`, `author_id`, `title`, `description`, `school_level`, `category` |
| `club_post_images` | 소모임 사진 (최대 2) | `id`, `post_id`, `storage_path`, `sort_order` |
| `club_comments` | 소모임 댓글 | `id`, `post_id`, `author_id`, `body` |
| `school_review_questions` | 운영자 등록 질문 | `id`, `text`, `sort_order`, `is_active` |
| `school_reviews` | 사용자별 학교 평가 | `id`, `school_id`, `user_id`, unique(`school_id`,`user_id`) |

**제약 조건으로 강제할 규칙**

- 학교급-카테고리 짝: `CHECK` 제약으로 `elementary`는 2개 값, `secondary`는 10개 값만 허용.
- 사진 개수: 삽입 트리거에서 나눔 4장·소모임 2장 초과 시 예외.
- 예약 전이: `available` → `reserved` → `completed`만 허용하는 트리거. `completed`에서
  나가는 전이는 모두 거부.
- 예약 중 댓글: `share_comments` 삽입 트리거에서 대상 글이 `reserved`면 거부. (R15)
- 닉네임 고유: `UNIQUE` 인덱스.
- 점수 범위: `CHECK (score BETWEEN 1 AND 5)`.

**RLS 방침**

- 모든 테이블에 RLS를 켠다.
- 헬퍼 함수 `is_approved()`(현재 사용자의 `profiles.status = 'approved'`)와 `is_admin()`을
  `SECURITY DEFINER`로 만들고 정책에서 재사용한다.
- 읽기: `is_approved()`인 경우에만 허용. `profiles`의 본인 행은 상태와 무관하게 읽을 수 있어야
  승인 대기 화면이 동작한다.
- 쓰기: `is_approved()` + 소유권 조건. 상태 변경은 글쓴이/예약자 조건을 정책에 넣는다.
- `item_types`, `school_review_questions`의 쓰기는 `is_admin()`만.
- `schools`, `school_search_cache`, `school_search_cache_items`는 **읽기만** 사용자
  세션에 열어준다. 쓰기 정책을 두지 않아 `anon`·`authenticated` 역할로는 INSERT/UPDATE가
  불가능하다. 캐시 채우기와 학교 저장은 라우트 핸들러에서 `SUPABASE_SERVICE_ROLE_KEY`로
  만든 서버 클라이언트가 수행한다. (R34)

**뷰**

- `user_carbon_totals` — 사용자별 `completed` 나눔 글의 `carbon_g` 합. (R17)
- `school_rating_summary` — 학교별·질문별 평균과 전체 평균, 참여자 수. (R23, R25)

두 뷰 모두 `security_invoker = true`로 만들어 기저 테이블의 RLS가 그대로 적용되게 한다.
뷰가 RLS 우회 통로가 되면 AC3이 무의미해진다.

**인덱스**

- `share_posts(author_id) WHERE status = 'completed'` — 누적 탄소량 집계용 부분 인덱스.
- `school_search_cache(query_key)` — unique.
- `school_search_cache_items(cache_id, rank)`.

**라우팅 구조**

```
app/
  (auth)/login, /signup
  (pending)/pending            승인 대기 안내
  (app)/share                  나눔 목록·상세·작성
  (app)/clubs                  소모임 목록·상세·작성
  (app)/schools                학교 검색·상세·평가
  (app)/me                     내 설정, 내 글, 탄소량
  admin/approvals              가입 승인
  admin/questions              평가 질문 관리
  api/schools/search           카카오 프록시
```

`middleware.ts`에서 세션과 `profiles.status`를 확인해 미승인 사용자를 `/pending`으로,
비로그인 사용자를 `/login`으로 보낸다. 이건 UX용이고, 실제 차단은 RLS가 한다.

**카카오 호출 형태**

`GET https://dapi.kakao.com/v2/local/search/keyword.json?query=<검색어>&category_group_code=SC4`
헤더 `Authorization: KakaoAK <KAKAO_REST_API_KEY>`. 응답의 `documents[]`에서
`id`, `place_name`, `road_address_name`, `address_name`, `x`(경도), `y`(위도)를 뽑아
클라이언트에 넘긴다. 나머지 필드는 버린다.

라우트 핸들러의 흐름은 이렇다.

1. 검색어를 정규화해 `query_key`를 만든다. (R30)
2. `school_search_cache`에서 `query_key`를 찾는다. 있고 `fetched_at`이 90일 이내면
   `school_search_cache_items`를 `rank` 순으로 조인해 결과를 만들고 **여기서 끝낸다.**
   카카오를 호출하지 않는다. (R30, R33)
3. 없거나 만료됐으면 카카오를 호출한다. (R31)
4. 결과 학교를 `kakao_place_id` 기준으로 `schools`에 upsert 한다. 서비스 롤 클라이언트를
   쓴다. (R22, R34)
5. 캐시 헤더를 upsert 하고, 기존 items를 지운 뒤 새 결과를 `rank`와 함께 넣는다.
   `fetched_at`을 갱신한다. (R31, R32)

카카오 호출은 이 한 곳에만 존재해야 한다. 테스트에서 호출 횟수를 세려면 그래야 한다.

## Risks And Open Decisions

**미확정 결정 (잠정 기본값으로 진행 중)**

1. **가입 승인 기준** — 잠정: 관리자 수동 승인만. 학교 이메일 도메인 자동 승인으로 바꾸면
   `profiles`에 도메인 검증 결과 컬럼이 붙고 T5의 승인 화면이 예외 처리 전용으로 축소된다.
   재직 증빙 첨부 방식이면 Storage 버킷과 파일 검토 UI가 추가되어 T5 범위가 커진다.
2. **탄소량 부여 방식** — 잠정: 글쓴이가 품목 유형을 고르면 `item_types.carbon_g`가
   글에 스냅샷으로 복사된다. 카테고리 고정 계수로 바꾸면 `item_types` 테이블이 사라지고
   카테고리 상수에 계수가 들어간다. 관리자 수동 부여면 `share_posts.carbon_g`가
   관리자 전용 쓰기 필드가 되고 승인 큐가 하나 더 생긴다.
3. **평가 질문 세트** — 잠정: 전국 공통 1세트. 학교급별 세트로 가면
   `school_review_questions`에 `school_level` 컬럼이, 학교별 등록이면 `school_id`가 붙고
   평균 집계 뷰의 그룹 기준이 바뀐다.

**위험**

- **카카오 응답 데이터 저장 범위 (확인 필요).** 캐싱 요구사항(R30~R33) 때문에 저장
  대상이 "사용자가 선택한 학교"에서 "검색 결과로 돌아온 모든 학교"로 넓어졌다. 카카오
  API 응답의 저장·캐싱 허용 범위는 카카오 서비스 약관과 운영 정책의 적용을 받고,
  데브톡에 관련 문의가 반복적으로 올라오는 주제다. **T21에 착수하기 전에 카카오 정책을
  확인하거나 데브톡으로 문의해 답을 받아 둔다.** 저장이 제한된다면 캐시 전략 자체를
  다시 설계해야 하고, R22·R30~R33과 마이그레이션 6이 통째로 바뀐다.
- 캐시 키가 정규화된 문자열 일치라서 "언남초"와 "언남초등학교"는 서로 다른 항목이 된다.
  히트율이 낮아지는 대신 동작이 단순하고 예측 가능하다. 의도한 선택이지만 실제
  히트율은 사람 검증에서 확인한다.
- 캐시 유효기간 90일 동안은 신설·이전·개명된 학교가 검색 결과에 반영되지 않는다.
  MVP 규모에서는 감수할 만하지만, 3월 학기 초에 문의가 들어올 수 있다.
- 카카오 `SC4` 카테고리에는 학교가 아닌 시설(학원, 어학원 등)이 섞여 들어올 수 있다.
  사람 검증 항목에 넣었다. 정확도가 문제가 되면 NEIS 학교기본정보 API로 교체하거나
  보강하는 것을 다음 단계에서 검토한다. MVP에서는 하지 않는다.
- `carbon_g`를 글에 스냅샷으로 저장하므로, 관리자가 계수 표를 바꿔도 과거 글의 값은
  변하지 않는다. 의도한 동작이다. 소급 반영이 필요하면 별도 결정이 필요하다.
- RLS 정책이 늘어나면 목록 쿼리 성능이 떨어질 수 있다. `is_approved()`를
  `SECURITY DEFINER` + `STABLE`로 만들어 행마다 재평가되지 않게 한다.
- 이메일 확인 메일 발송은 Supabase 기본 SMTP를 쓰면 발송량 제한이 있다. 운영 전에
  외부 SMTP 연결이 필요하다. MVP 개발 중에는 문제되지 않는다.
- 승인 대기 화면이 필요하므로 `profiles`의 본인 행 읽기 정책만 상태 조건에서 예외다.
  이 예외가 다른 정책으로 새지 않도록 T20 검증 스크립트에서 확인한다.

## Implementation Result Report Contract

구현이 끝나면 아래 형식으로 보고한다.

1. **완료한 태스크** — T1~T22 중 완료한 항목과 각각의 실제 산출 파일 경로.

3. **마이그레이션** — 추가된 마이그레이션 파일 목록과 각 파일이 만드는 객체 요약,
   되돌리는 방법.
4. **환경 변수** — 실제로 필요했던 변수 이름 목록. PRD에 없던 변수가 생겼다면 이유.
5. **수용 기준 결과** — AC1~AC22 각각에 대해 통과/실패/미확인. 실패는 재현 방법까지.

8. **PRD와 달라진 점** — 구현 중 불가피하게 다르게 만든 부분과 근거. 없으면 "없음".
